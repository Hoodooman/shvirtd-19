# Нагрузки Kubernetes
Kubernetes предоставляет несколько встроенных API для декларативного управления вашими рабочими нагрузками и их компонентами.

В конечном итоге, ваши приложения работают в виде контейнеров внутри Pod (подов). Однако управление отдельными подами было бы очень трудоемким. Например, если под падает, вам нужно запустить новый под для его замены. Kubernetes может делать это за вас.

Вы используете API Kubernetes для создания объекта рабочей нагрузки, который представляет собой абстракцию более высокого уровня, чем Pod. Затем система управления (control plane) Kubernetes автоматически управляет подами на основе спецификации, которую вы определили в этом объекте.

Встроенные API для управления рабочими нагрузками:

# Основные API рабочих нагрузок
1. Deployment (Развертывание)
- Назначение: Это самый распространенный способ запуска статического (stateless) приложения в кластере. Он гарантирует, что работающее указанное количество идентичных подов постоянно.

- Механизм: Использует объект ReplicaSet (Набор реплик) "под капотом" для управления репликацией и масштабированием подов.

- Филосория подов: Поды являются взаимозаменяемыми. Если под выходит из строя, Deployment заменяет его новым, идентичным подом. Новый под получает собственный IP-адрес и хранилище.

- Сценарий использования: Веб-серверы, API, микросервисы — любые приложения, где запросы могут быть обработаны любым экземпляром, не зависящим от уникального локального состояния.

2. StatefulSet (Набор с состоянием)
- Назначение: Управляет развертыванием и масштабированием набора подов, где каждый под имеет уникальную, постоянную идентичность.

- Механизм: Поды создаются последовательно, в упорядоченном manner, и имеют стабильные, предсказуемые имена (например, web-0, web-1, web-2). Эта стабильность критически важна для их идентичности. Каждый под часто связан с уникальным томом хранения данных (PersistentVolume).

- Филосория подов: Поды не являются взаимозаменяемыми. Каждый под уникально привязан к своему постоянному хранилищу и идентичности.

- Сценарий использования: Stateful-приложения, такие как базы данных (Kafka, кластеры MySQL, Elasticsearch), где каждому экземпляру нужно собственное выделенное хранилище и стабильный сетевой идентификатор для обнаружения.

3. DaemonSet (Набор демонов)
- Назначение: Гарантирует, что копия пода работает на всех (или некоторых) узлах в кластере. Когда новые узлы добавляются в кластер, на них автоматически создаются поды.

- Механизм: Напрямую размещает по одному поду на каждом узле, обходя обычные правила планировщика (scheduler).

- Филосория подов: Поды предоставляют сервис уровня узла, аналогичный системному демону в UNIX.

- Сценарии использования:

  - Работа кластера: Плагины сетей (например, Calico), плагины хранения (например, Ceph).

  - Управление узлами: Демоны сбора логов (например, Fluentd), агенты мониторинга (например, Prometheus Node Exporter).

  - Управление оборудованием: Демоны драйверов GPU на узлах, где установлены GPU.

4. Job и CronJob (Задача и Периодическая задача)
- Назначение: Запуск задач, которые должны выполниться до завершения и остановиться, а не работать непрерывно.

- Job: Определяет разовую задачу. Kubernetes запускает один или несколько подов до тех пор, пока указанное количество из них не завершится успешно.

- CronJob: Задача (Job), которая запускается по расписанию, определенному с помощью cron-синтаксиса (например, "0 * * * *" для запуска каждый час).

- Сценарии использования: Пакетная обработка данных, резервное копирование баз данных, отправка ежедневных отчетов по email, запуск скрипта однократной миграции данных.

# Сравнительная таблица

| Тип рабочей нагрузки | Философия подов                     | Основной сценарий использования    | Ключевая особенность                                                     |
|----------------------|-------------------------------------|------------------------------------|--------------------------------------------------------------------------|
| Deployment           | Взаимозаменяемые                    | Статические приложения (stateless) | Обновления без простоя, откаты, масштабирование                          |
| StatefulSet          | Уникальные идентичность и хранилище | Stateful-приложения                | Стабильный сетевой ID, упорядоченное развертывание, постоянное хранилище |
| DaemonSet            | Сервис уровня узла                  | Сервисы для кластера и узлов       | Один под на каждом (выбранном) узле                                      |
| Job / CronJob        | Выполнение до завершения            | Пакетные и scheduled задачи        | Запуск задачи с гарантией успешного завершения                           |

# Заключение
Выбор правильного объекта рабочей нагрузки полностью зависит от характера приложения, которое вам нужно запустить:

- Stateless и масштабируемое? Используйте Deployment.

- Требует устойчивой идентичности и хранилища? Используйте StatefulSet.

- Должно работать на каждом узле? Используйте DaemonSet.

- Пакетная или scheduled задача? Используйте Job или CronJob.

Эта абстракция является фундаментальной частью Kubernetes, которая делает его мощной платформой для развертывания разнообразных типов приложений.

# Pod
Pod (Под, контейнер) — это наименьшая и простейшая развертываемая единица в модели объектов Kubernetes. Он представляет собой один экземпляр запущенного процесса в вашем кластере.

# Ключевые характеристики Pod:
1. Группа контейнеров: Pod — это логический "хост" для одного или нескольких контейнеров приложения.

- Наиболее частый случай: Один контейнер. Здесь Pod выступает в роли обертки вокруг этого контейнера.

- Продвинутый случай: Несколько тесно связанных контейнеров, которым необходимо совместно использовать ресурсы (такие как хранилище и сеть) и работать вместе как единое целое (например, веб-сервер и вспомогательный (sidecar) контейнер, который обновляет его файлы).

2. Общее пространство: Контейнеры внутри Pod разделяют:

- Сеть: Один IP-адрес и пространство портов. Они могут обращаться друг к другу через localhost.

- Хранилище: Набор общих томов (Volumes), что позволяет им обмениваться данными.

3. Эфемерная природа: Pod'ы созданы быть одноразовыми. Они создаются, получают уникальный ID, планируются на выполнение на узле (Node) и работают до завершения или удаления. Если узел выходит из строя, Pod'ы на нем не восстанавливаются; вместо этого они заменяются новыми.

4. Управляются контроллерами: Pod'ы редко создаются напрямую. Вместо этого используются ресурсы рабочих нагрузок (Workload Resources), такие как Deployments (деплойменты), StatefulSets (сеты состояния) или Jobs (задания), которые управляют Pod'ами за вас. Эти контроллеры handle replication (репликацию), rollout (развертывание) и automatic healing (автоматическое восстановление) (например, замену failed Pod'а).

5. Шаблон Pod (Pod Template): Ресурсы рабочих нагрузок создают Pod'ы из шаблона Pod, который представляет собой спецификацию для создания Pod'ов, встроенную в конфигурацию ресурса.

# Аналогия
Представьте себе Pod как логическую машину (виртуальный сервер):

- Контейнеры внутри Pod'а — это процессы, работающие на одной и той же машине.

- Они могут легко "общаться" друг с другом (через localhost) и имеют доступ к одним и тем же "дискам" (томам).

# Простой пример Pod
YAML-манифест ниже определяет Pod с именем nginx с одним контейнером, запускающим образ nginx:1.14.2.

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: nginx
spec:
  containers:
  - name: nginx
    image: nginx:1.14.2
    ports:
    - containerPort: 80
```

# Краткий итог:
- Назначение: Фундаментальный строительный блок для развертывания приложений.
- Содержимое:	Один или несколько тесно связанных контейнеров.
- Сетевое взаимодействие:	Контейнеры делят IP-адрес и могут общаться через localhost.
- Хранилище:	Контейнеры имеют доступ к общим томам (Volumes).
- Управление:	Обычно создаются и управляются контроллерами более высокого уровня (Deployments и т.д.).
- Время жизни:	Эфемерны; создаются и уничтожаются по мере необходимости.


# Services
Поды (Pods) в Kubernetes — временные и неустойчивые. Они могут создаваться, уничтожаться и перемещаться между узлами. Каждый Pod получает свой собственный IP-адрес, но эти адреса непостоянны.

Проблема: Если набор backend-подов предоставляет услуги frontend-подам, как frontends узнают, к каким текущим, работоспособным backends подключаться, если их IP-адреса постоянно меняются?

Решение: Ресурс Service (Сервис).

# Что такое Service?
Service — это стабильный абстракционный уровень, который определяет логическую группу подов (обычно через selector — селектор) и политику доступа к ним. Он предоставляет единственный, постоянный IP-адрес и имя хоста, которые могут использовать клиенты. При этом сам Service автоматически направляет трафик на правильные backend-поды, даже когда они меняются.

### Ключевые характеристики:
- Стабильный IP-адрес (ClusterIP): Service получает виртуальный IP, который не меняется в течение всего времени его жизни.

- Балансировка нагрузки: Автоматически распределяет трафик между всеми здоровыми подами, соответствующими его селектору.

- Слабая связность (Loose Coupling): Клиентам (frontend) нужно знать только о Service, а не об отдельных подах за ним.

- Обнаружение сервисов (Service Discovery): Podы могут находить Service через переменные окружения или, что чаще, через DNS.

# Определение Service: структура YAML
Базовое определение Service targets pods using a label selector.

```yaml
apiVersion: v1
kind: Service # Вид ресурса - Сервис
metadata:
  name: my-service # Название сервиса
spec:
  selector: # Выбирает поды с этими метками
    app.kubernetes.io/name: MyApp
  ports:
    - protocol: TCP
      port: 80       # Порт, который слушает Service
      targetPort: 9376 # Порт на целевых подах
  # type: ClusterIP - тип по умолчанию, можно не указывать
```

# Типы Service (Service Types)
Свойство type в спецификации определяет, как Service предоставляется наружу. Каждый последующий тип расширяет предыдущий.

| Тип                      | Описание                                                                                                                                                                                    | Сценарий использования                                                                                                                |
|--------------------------|---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|---------------------------------------------------------------------------------------------------------------------------------------|
| ClusterIP (По умолчанию) | Предоставляет Service на внутреннем IP-адресе кластера. Service доступен только изнутри кластера.                                                                                           | Внутренняя коммуникация между микросервисами (например, бэкенд API общается с базой данных).                                          |
| NodePort                 | Предоставляет Service на одном и том же статическом порту каждого IP-адреса Node (узла). Создает Service типа ClusterIP для маршрутизации. Доступен извне кластера по <IP_узла>:<NodePort>. | Для случаев, когда нужно предоставить сервис напрямую с узлов, часто для кастомных решений балансировки или вне облачных провайдеров. |
| LoadBalancer             | Создает внешний облачный балансировщик нагрузки (например, AWS ELB, GCP Load Balancer), который указывает на Service. Автоматически создает Service типов NodePort и ClusterIP.             | Стандартный способ предоставить сервис напрямую в интернет у облачных провайдеров.                                                    |
| ExternalName             | Сопоставляет Service с DNS-именем (например, my.database.example.com). Проксирование или переадресация не выполняются.                                                                      | Для интеграции с внешними сервисами вне кластера. DNS-сервер Kubernetes вернет CNAME-запись.                                          |

# Продвинутые концепции
1. Headless Services (Безголовые сервисы):
  - Создается путем установки spec.clusterIP: None.
  - Нет балансировки нагрузки или единого IP. Полезен для stateful-приложений или когда нужно прямое взаимодействие между подами (например, базы данных вроде Kafka или MongoDB, которым нужно обнаруживать всех своих участников).
  - DNS возвращает несколько A/AAAA записей (IP-адреса подов) вместо одного IP-адреса Service.

2. Services Without Selectors (Сервисы без селекторов):

  - Используются для абстракции сервисов вне вашего Kubernetes-кластера (например, база данных в локальном ЦОД).

  - Вы вручную создаете ресурс EndpointSlice (или устаревший Endpoints), чтобы определить сетевые адреса внешних endpoint'ов.

3. EndpointSlices:

  - Современная, масштабируемая замена старого API Endpoints.

  - Они отслеживают сетевые endpoints (IP-адреса подов) для Service. Контроллер автоматически управляет ими, когда у Service есть селектор.

4. Session Affinity (Сходство сеансов):

  - По умолчанию Service балансирует соединения случайным образом между подами.

  - Установка sessionAffinity: ClientIP гарантирует, что соединения с одного IP-адреса клиента будут перенаправляться на один и тот же Pod.

# Как обнаружить Service (изнутри кластера)
1. Переменные окружения: При запуске пода kubelet добавляет переменные окружения для каждого активного Service (например, MY_SERVICE_SERVICE_HOST=10.96.42.1). Не предпочтительный метод из-за проблем с порядком создания.

2. DNS (Рекомендуется): Предпочтительный метод. Кластерный DNS-сервер (например, CoreDNS) автоматически создает DNS-запись для сервисов.

 - my-service.my-namespace.svc.cluster.local резолвится в ClusterIP Service.

 - Within the same namespace, you can simply use my-service.

 - В пределах того же пространства имен (namespace) можно использовать просто my-service.

# Итог: Что и когда использовать
 - Внутренняя коммуникация в кластере: Используйте ClusterIP.

 - Предоставление приложения в интернет у облачного провайдера: Используйте LoadBalancer.

 - Предоставление приложения для кастомного/on-prem доступа: Используйте NodePort.

 - Указание на внешний сервис по имени: Используйте ExternalName.

 - Для StatefulSets или прямого обнаружения подов: Используйте Headless Service (clusterIP: None).

 - Для продвинутой маршрутизации HTTP/HTTPS трафика: Используйте ресурс Ingress (который работает поверх Services) или новый Gateway API.


# Deployment
Deployment — это объект Kubernetes, который предоставляет декларативный способ управления набором идентичных Pods (через ReplicaSet) для без состояния (stateless) приложения. Вы описываете желаемое состояние (например, «запусти три реплики моего приложения с версией образа 1.16.1»), и Контроллер Deployment автоматически и постепенно изменяет текущее состояние, чтобы соответствовать желаемому.

# Ключевые сценарии использования (Use Cases)
- Развертывание ReplicaSet: Запуск новой версии приложения.

- Обновление Pods: Объявите новое состояние (например, обновите образ контейнера), и Deployment выполнит контролируемое rolling-обновление.

- Откат к предыдущей ревизии: Вернитесь к более ранней, стабильной версии, если обновление не удалось.

- Масштабирование Deployment: Увеличьте или уменьшите количество реплик для обработки большей или меньшей нагрузки.

- Приостановка и возобновление обновлений: Внесите несколько изменений в конфигурацию Deployment, прежде чем запускать новое развертывание.

# Создание Deployment
Deployment определяется с помощью YAML-манифеста.

Пример: nginx-deployment.yaml

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: nginx-deployment
  labels:
    app: nginx
spec:
  replicas: 3 # Желаемое количество Pods
  selector: # Как Deployment находит Pods для управления
    matchLabels:
      app: nginx
  template: # Шаблон Pod
    metadata:
      labels:
        app: nginx # Должен совпадать с селектором выше
    spec:
      containers:
      - name: nginx
        image: nginx:1.14.2 # Образ контейнера
        ports:
        - containerPort: 80
```
Применение Deployment:

```bash
kubectl apply -f nginx-deployment.yaml
```
Проверка статуса:

```bash
kubectl get deployments
# NAME READY UP-TO-DATE AVAILABLE AGE
# nginx-deployment 3/3 3 3 18s

kubectl get rs # Посмотреть созданный ReplicaSet
kubectl get pods --show-labels # Посмотреть созданные Pods
```

# Обновление Deployment
Развертывание (rollout) запускается только при изменении шаблона Pod (.spec.template), например, при обновлении образа контейнера.

Обновление образа:

```bash
kubectl set image deployment/nginx-deployment nginx=nginx:1.16.1
# или
kubectl edit deployment/nginx-deployment # Редактировать манифест вручную
```
Что происходит во время обновления:
Контроллер Deployment создает новый ReplicaSet и начинает rolling-обновление:

1. Увеличивает масштаб нового ReplicaSet (например, +1 pod).

2. Уменьшает масштаб старого ReplicaSet (например, -1 pod).

3. Повторяет этот процесс, пока все Pods в новом ReplicaSet не будут работать, а все Pods в старом ReplicaSet не будут завершены и удалены (terminated)*.<br>
*Kubernetes чаще используется термин «завершены» (terminated) или «удалены» (deleted).

Это потому, что процесс остановки Pod происходит в несколько этапов и не всегда мгновенный:

1. Инициация завершения: Контроллер отправляет сигнал SIGTERM процессам внутри Pod'a. Это уведомление, что пора начать корректно завершать работу (завершить открытые соединения, сохранить состояние и т.д.).

2. Ожидание: Kubernetes ждет определенное время (terminationGracePeriodSeconds, по умолчанию 30 секунд), чтобы приложение могло gracefully завершиться.

3. Принудительное завершение: Если по истечении этого времени Pod еще не остановился, отправляется сигнал SIGKILL, и Pod принудительно удаляется с узла.

Таким образом, Pod'ы из старого ReplicaSet не просто "уничтожаются", а проходят процесс управляемого завершения, чтобы минимизировать влияние на пользователей.

Эта стратегия гарантирует доступность приложения, соблюдая значения по умолчанию:

- maxUnavailable: 25% (Гарантирует, что 75% желаемых Pods всегда доступны).

- maxSurge: 25% (Позволяет общему количеству Pods достигать до 125% от желаемого количества во время обновления).

Мониторинг процесса обновления:

```bash
kubectl rollout status deployment/nginx-deployment
kubectl describe deployments
```

# Откат Deployment
Если развертывание fails (например, из-за сломанного образа), вы можете легко откатиться.

1. Проверить историю развертываний:

```bash
kubectl rollout history deployment/nginx-deployment
# deployments "nginx-deployment"
# REVISION CHANGE-CAUSE
# 1 <none>
# 2 kubectl set image...nginx:1.16.1
# 3 kubectl set image...nginx:1.161 # Сломанная версия
```
2. Откат к предыдущей версии:

```bash
kubectl rollout undo deployment/nginx-deployment # Откатывается к предыдущей ревизии
# или
kubectl rollout undo deployment/nginx-deployment --to-revision=2 # Откат к конкретной ревизии
```
3. Проверить откат:

```bash
kubectl get deployment nginx-deployment
kubectl describe deployment nginx-deployment
```

# Полезные операции
Масштабирование Deployment:

```bash
kubectl scale deployment/nginx-deployment --replicas=5
```
Приостановка и возобновление обновления:
Это позволяет вам вносить несколько изменений, не запуская обновление после каждого промежуточного шага.

```bash
kubectl rollout pause deployment/nginx-deployment # Приостановить
kubectl set image deployment/nginx-deployment nginx=nginx:1.17.0 # Изменение 1
kubectl set resources deployment/nginx-deployment -c=nginx --limits=cpu=200m,memory=512Mi # Изменение 2
kubectl rollout resume deployment/nginx-deployment # Возобновить - начнется единое обновление
```
Установка дедлайна для обновления:
Если обновление зависло, вы можете указать Kubernetes пометить его как не удавшееся по истечении указанного времени.

```bash
kubectl patch deployment/nginx-deployment -p '{"spec":{"progressDeadlineSeconds":600}}' # 10 минут
```
Политика очистки (История ревизий):
Контролируйте, сколько старых ReplicaSet сохраняется для отката (по умолчанию 10).

```yaml
spec:
  revisionHistoryLimit: 5
```

# Важные заметки и лучшие практики
- Неизменяемый селектор: В apps/v1 селектор Deployment (.spec.selector) неизменяем после создания. Планируйте свои метки тщательно.

- Хэш шаблона Pod (Pod Template Hash): Контроллер добавляет метку pod-template-hash к каждому Pod и ReplicaSet. Не изменяйте эту метку.

- Не управляйте управляемыми ReplicaSet: Никогда не управляйте напрямую ReplicaSet, созданными Deployment. Позвольте контроллеру делать это.

- Непересекающиеся селекторы: Убедитесь, что у Deployments и других контроллеров (как StatefulSets) нет пересекающихся селекторов, чтобы избежать конфликтов.

- Завершающиеся Pods (Terminating): Pods, которые завершают работу, не считаются «доступными» (available), но все еще потребляют ресурсы, пока полностью не终止 (terminate).


# Init Containers
Init containers — это специализированные контейнеры, которые запускаются и завершают свою работу до того, как начнут работать основные контейнеры приложения в Pod. Они используются для установки, инициализации и предварительных проверок.

#### 1. Ключевые характеристики
- Запуск до завершения: Они должны выполнить свою работу и завершиться со статусом "Успех".

- Последовательное выполнение: Они запускаются строго один за другим. Каждый следующий контейнер ждет успешного завершения предыдущего.

- Блокируют запуск приложения: Основные контейнеры приложения не запустятся, пока все init containers не завершатся успешно.

- Обработка сбоев: Если init container падает, он перезапускается (в соответствии с restartPolicy Pod'а). Если для Pod установлен restartPolicy: Never и init container fails, весь Pod помечается как failed.

#### 2. Как их определить
Вы определяете init containers в спецификации Pod в поле initContainers, которое находится на том же уровне, что и основное поле containers.

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: myapp-pod
spec:
  containers:
  - name: myapp-container
    image: my-app:1.0
    # Определение основного приложения...
  initContainers: # Вот здесь определяются init containers
  - name: init-service
    image: busybox:1.28
    command: ['sh', '-c', 'ваш-скрипт-инициализации']
  - name: init-db
    image: busybox:1.28
    command: ['sh', '-c', 'другая-команда-инициализации']
```
#### 3. Отличия от обычных контейнеров

| Особенность      | Init Containers                                              | Обычные контейнеры приложения                                       |
|------------------|--------------------------------------------------------------|---------------------------------------------------------------------|
| Цель             | Настройка и инициализация                                    | Запуск основного приложения                                         |
| Выполнение       | Запускаются последовательно и завершаются                    | Работают параллельно в течение всего времени жизни Pod'а            |
| Пробы (Probes)   | НЕ поддерживают livenessProbe, readinessProbe, startupProbe  | Поддерживают все пробы для управления состоянием и жизненным циклом |
| Готовность Pod'а | Pod не готов, пока все init containers не завершатся успешно | Готовность Pod'а зависит от их readinessProbe                       |

#### 4. Отличия от Sidecar контейнеров
- Init Containers: Выполняются и завершаются до запуска основного приложения. Их задача — подготовить среду.

- Sidecar Контейнеры: Запускаются до или вместе с основным приложением и продолжают работать alongside с ним на протяжении всего его жизненного цикла (например, сборщик логов, прокси service mesh). Sidecars поддерживают пробы.

#### 5. Распространенные сценарии использования и примеры
Init containers идеальны для задач, которые должны выполниться до старта вашего приложения:

1. Ожидание зависимостей: Ожидание, пока база данных или сервис станут доступны.

```yaml
command: ['sh', '-c', 'until nslookup myservice; do echo "ждем..."; sleep 2; done']
```
2. Динамическая конфигурация: Генерация файлов конфигурации с использованием переменных окружения или шаблонов до того, как основное приложение загрузит их.

3. Регистрация Pod'а: Регистрация Pod'а во внешней системе, используя его имя или IP (через Downward API).

4. Клонирование репозиториев: Клонирование кода в volume, который будет использовать основное приложение.

5. Безопасность: Запуск команд setup, для которых требуются инструменты (например, curl, sed, openssl), без необходимости включать их в основной безопасный образ приложения.

6. Практический пример из текста
Этот Pod не запустит основное приложение, пока сервисы myservice и mydb не станут обнаруживаемы через DNS.

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: myapp-pod
spec:
  containers:
  - name: myapp-container
    image: busybox:1.28
    command: ['sh', '-c', 'echo Приложение работает! && sleep 3600']
  initContainers:
  - name: init-myservice
    image: busybox:1.28
    command: ['sh', '-c', "until nslookup myservice.$(cat /var/run/secrets/kubernetes.io/serviceaccount/namespace).svc.cluster.local; do echo 'ожидание myservice'; sleep 2; done"]
  - name: init-mydb
    image: busybox:1.28
    command: ['sh', '-c', "until nslookup mydb.$(cat /var/run/secrets/kubernetes.io/serviceaccount/namespace).svc.cluster.local; do echo 'ожидание mydb'; sleep 2; done"]
```
Как использовать:

1. Примените Pod (kubectl apply -f myapp.yaml): он зависнет в статусе Init.

2. Создайте сервисы myservice и mydb.

3. Init containers завершатся, и основной контейнер приложения запустится.

Проверить статус:

```bash
kubectl get pod myapp-pod
```
Посмотреть логи init container:

```bash
kubectl logs myapp-pod -c init-myservice
```

7. Важное поведение
- Лимиты ресурсов: Эффективный запрос ресурсов для Pod'а вычисляется как наибольшее из:

  - Суммы запросов всех контейнеров приложения, ИЛИ

  - Самого большого запроса от любого отдельного init container.
Это означает, что init container может временно запросить больше CPU/памяти для настройки, чем нужно самому приложению.

- Неизменяемость: Вы не можете обновить большинство полей init container (например, его команду) в работающем Pod'е; можно обновить только его образ. Для других изменений Pod нужно пересоздать.

- Идемпотентность: Код в init container должен быть написан так, чтобы его можно было безопасно запускать (идемпотентно), на случай перезапуска Pod'а.

- Статус Pod'а: Pod с работающими init containers имеет статус STATUS: Init:0/2 (где 2 — общее количество init containers) и условие Initialized: False.

# Ingress
Ingress — это объект API в Kubernetes, который предоставляет интеллектуальный шлюз уровня 7 (HTTP/HTTPS) для управления внешним доступом к сервисам внутри кластера. Он действует как обратный прокси, маршрутизируя входящий трафик на основе правил, которые вы определяете (имена хостов, пути и т.д.).

#### 1. Ключевая концепция: Ingress Resource vs. Ingress Controller
Это самое важное различие:

Ресурс Ingress (Ingress Resource): YAML-файл, который создаете вы. Это набор правил для маршрутизации трафика (например, «отправлять запросы для api.example.com на api-service»).

Контроллер Ingress (Ingress Controller): Приложение, которое выполняет эти правила. Это сервер обратного прокси (такой как Nginx, Traefik или HAProxy), работающий в вашем кластере. Вы должны развернуть Ingress Controller, чтобы ваши правила Ingress вообще имели какой-либо эффект.

Аналогия: Ресурс Ingress — это дорожные знаки и карта, а контроллер Ingress — это автомобиль, который едет по ним.

#### 2. Ключевые возможности
Ingress предоставляет несколько важных функций, которых нет у более простых сервисов типа NodePort или LoadBalancer:

Виртуальный хостинг по имени (Name-Based Virtual Hosting): Маршрутизировать несколько доменных имен на разные сервисы через один IP-адрес.

Маршрутизация на основе пути (Path-Based Routing): Направлять трафик на разные сервисы в зависимости от пути в URL (например, /shop на один сервис, /blog на другой).

Завершение TLS/SSL (TLS/SSL Termination): Управление SSL-сертификатами на уровне Ingress, расшифровка трафика до того, как он попадет в кластер. Это упрощает управление сертификатами для ваших сервисов.

Балансировка нагрузки (Load Balancing): Распределение трафика между подами (pods) сервиса.

#### 3. Структура ресурса Ingress (YAML)
Основная спецификация Ingress состоит из двух основных частей: rules и, опционально, tls.

```yaml
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: my-ingress
  annotations:                           # Контроллер-специфичные настройки
    nginx.ingress.kubernetes.io/rewrite-target: /
spec:
  ingressClassName: nginx                # Указывает, какой контроллер должен этим управлять
  tls:                                  # Секция TLS/SSL
  - hosts:
      - myapp.example.com
    secretName: my-tls-secret           # Secret Kubernetes, содержащий cert и key
  rules:                                # Правила маршрутизации
  - host: myapp.example.com             # Правило 1: Совпадение по этому имени хоста
    http:
      paths:
      - path: /api
        pathType: Prefix
        backend:
          service:
            name: api-service           # Отправить на этот сервис...
            port:
              number: 8080              # ...на этот порт
      - path: /
        pathType: Prefix
        backend:
          service:
            name: web-frontend
            port:
              number: 80
```
#### 4. Типы путей (Path Types)
Параметр pathType является обязательным и определяет, как работает сопоставление путей:

Prefix: Совпадение на основе префикса пути URL (например, /api/ соответствует /api/v1/ и /api/v2/getUser).

Exact: Точное совпадение пути URL с учетом регистра.

ImplementationSpecific: Интерпретация зависит от реализации Ingress Controller.

#### 5. IngressClass
Был введен для формального определения различных типов контроллеров Ingress (например, "nginx", "traefik", "gce").

Заменяет устаревшую аннотацию kubernetes.io/ingress.class.

Позволяет пометить один класс как используемый по умолчанию (ingressclass.kubernetes.io/is-default-class: "true"), чтобы ресурсы Ingress без указанного класса использовались этим контроллером.

#### 6. Распространенные примеры использования

| Сценарий использования                | Описание                                                                                                    | Ключевое поле в spec            |
|---------------------------------------|-------------------------------------------------------------------------------------------------------------|---------------------------------|
| Простое ветвление (Fanout)            | Одно доменное имя, несколько путей к разным сервисам (например, example.com/api, example.com/web).          | rules[*].http.paths             |
| Виртуальный хостинг по имени          | Несколько доменных имен на одном IP (например, blog.example.com -> Сервис A, shop.example.com -> Сервис B). | rules[*].host                   |
| Завершение TLS                        | Защита одного или нескольких хостов с помощью HTTPS.                                                        | tls[*].hosts, tls[*].secretName |
| Сервис по умолчанию (Default Backend) | Обрабатывает все запросы, которые не соответствуют ни одному определенному правилу.                         | defaultBackend                  |

#### 7. Важные примечания и предостережения
Различия между контроллерами: Представленный YAML является общим. Всегда консультируйтесь с документацией вашего конкретного Ingress Controller. Аннотации (например, nginx.ingress.kubernetes.io/rewrite-target) и конкретное поведение могут значительно отличаться.

Не для TCP/UDP: Ingress предназначен только для трафика HTTP/HTTPS. Для предоставления доступа к другим протоколам (например, базы данных) используйте Service.Type=NodePort или Service.Type=LoadBalancer.

Будущее — Gateway API: В тексте отмечается, что API Ingress «заморожен». Для более сложных сценариев использования (например, межпространственная маршрутизация, детальное управление трафиком) рекомендуется использовать новый Gateway API. Он спроектирован так, чтобы быть более выразительным и ориентированным на роли.

## Если кратко:
Используйте Ingress, когда вам нужно предоставить доступ к нескольким HTTP-сервисам из интернета под разными доменными именами или путями, с завершением TLS и балансировкой нагрузки уровня 7. Не забудьте сначала установить и настроить Ingress Controller, такой как Nginx Ingress или Traefik.

# Volumes
## Что такое тома Kubernetes?
Тома предоставляют контейнерам в Pod'ах доступ к данным и возможность обмена файлами через файловую систему. Они решают две основные проблемы:

Сохранность данных: Файлы в контейнерах эфемерны - при остановке контейнера все данные теряются. Тома сохраняют данные.

Общее хранилище: Позволяют контейнерам в одном Pod'е совместно использовать файлы.

# Основные типы томов
## Актуальные и рекомендуемые:
- configMap - для конфигурационных данных

- emptyDir - временное хранилище (исчезает с удалением Pod'а)

- hostPath - монтирование файлов с узла (используйте осторожно!)

- nfs - сетевая файловая система

- persistentVolumeClaim (PVC) - постоянное хранилище

- secret - для секретных данных

- local - локальные диски как PersistentVolume

# Устаревшие/удаленные (переход на CSI драйверы):
- awsElasticBlockStore, azureDisk, azureFile, cephfs, cinder, gcePersistentDisk, gitRepo, glusterfs, rbd, vsphereVolume

# Конфигурация томов
## Пример emptyDir:
```yaml
apiVersion: v1
kind: Pod
metadata:
  name: test-pd
spec:
  containers:
  - image: registry.k8s.io/test-webserver
    name: test-container
    volumeMounts:
    - mountPath: /cache
      name: cache-volume
  volumes:
  - name: cache-volume
    emptyDir:
      sizeLimit: 500Mi
      medium: Memory  # Хранить в RAM
```
## Пример configMap:
```yaml
apiVersion: v1
kind: Pod
metadata:
  name: configmap-pod
spec:
  containers:
    - name: test
      image: busybox:1.28
      volumeMounts:
        - name: config-vol
          mountPath: /etc/config
  volumes:
    - name: config-vol
      configMap:
        name: log-config
        items:
          - key: log_level
            path: log_level.conf
```
# Ключевые особенности
## subPath - монтирование поддиректорий:
```yaml
volumeMounts:
- mountPath: /var/lib/mysql
  name: site-data
  subPath: mysql  # Только поддиректория mysql
```
# Распространение монтирования (Mount Propagation):
- None - по умолчанию, без распространения

- HostToContainer - монтирования с узла видны в контейнере

- Bidirectional - двустороннее распространение (требует привилегий)

# Только для чтения:
```yaml
volumeMounts:
- mountPath: /config
  name: config-volume
  readOnly: true  # Только чтение
```
# Рекомендации по использованию
## Безопасность:
- 🔒 Избегайте hostPath - потенциальная угроза безопасности

- 🔒 Используйте readOnly для configMap и secret

- 🔒 Bidirectional mount propagation только для привилегированных контейнеров

# Сохранность данных:
- 💾 Для временных данных: emptyDir

- 💾 Для постоянных данных: PersistentVolumeClaim

- 💾 Для конфигурации: configMap и secret

# Современные подходы:
- 🚀 Используйте CSI драйверы вместо устаревших in-tree плагинов

- 🚀 PersistentVolumeClaim для production-окружения

- 🚀 Local volumes для производительности (но учитывайте доступность)

# Миграция на CSI
Kubernetes переходит на Container Storage Interface (CSI) драйверы:

- Больше возможностей для storage-провайдеров

- Лучшая поддержка новых функций

- Независимость от релизов Kubernetes

# Важные предупреждения
## hostPath риски:
```yaml
# НЕ РЕКОМЕНДУЕТСЯ для production!
volumes:
- name: dangerous-volume
  hostPath:
    path: /etc/kubernetes  # Опасный путь!
    type: Directory
```
## emptyDir ограничения:
- Данные теряются при удалении Pod'а

- Ограничивайте размер через sizeLimit

- Для памяти используйте medium: Memory

# Лучшие практики
1. Конфигурация: configMap + readOnly

2. Временные данные: emptyDir с ограничениями

3. Постоянные данные: PVC + CSI драйвер

4. Секреты: secret volumes (никогда не в образы!)

5. Безопасность: минимальные привилегии, readOnly когда возможно

Тома Kubernetes предоставляют гибкую систему хранения данных - от временных файлов до высокодоступных распределенных хранилищ. Выбирайте тип тома в зависимости от требований к сохранности, безопасности и производительности.


# Secrets
# Что такое Secrets?
Secrets (Секреты) - это объекты Kubernetes, которые содержат конфиденциальные данные:

- Пароли, токены, ключи

- Учетные данные для аутентификации

- TLS-сертификаты

Преимущества использования Secrets:

- Не хранить чувствительные данные в коде приложения

- Отдельное управление конфиденциальными данными

- Меньший риск exposure при работе с Pods

# ⚠️ Важные предупреждения безопасности
По умолчанию Secrets НЕ зашифрованы в etcd!

- Любой с доступом к API может читать/изменять Secrets

- Любой, кто может создавать Pods в namespace, может читать Secrets в этом namespace

Меры безопасности:

1. Включите Encryption at Rest для Secrets

2. Настройте RBAC с минимальными привилегиями

3. Ограничьте доступ Secrets конкретным контейнерам

4. Рассмотрите внешние хранилища секретов

# Типы Secrets
# 1. Opaque (Произвольные данные)
```yaml
apiVersion: v1
kind: Secret
metadata:
  name: my-secret
type: Opaque
data:
  username: YWRtaW4=  # admin в base64
  password: c2VjcmV0MTIz  # secret123 в base64
```
# 2. TLS Secrets
```yaml
apiVersion: v1
kind: Secret
metadata:
  name: tls-secret
type: kubernetes.io/tls
data:
```

# Создание Secrets
### Через kubectl
```bash
# Из literal значений
kubectl create secret generic my-secret \
  --from-literal=username=admin \
  --from-literal=password=secret123

# Из файлов
kubectl create secret generic my-secret \
  --from-file=./username.txt \
  --from-file=./password.txt

# TLS Secret
kubectl create secret tls tls-secret \
  --cert=path/to/cert.pem \
  --key=path/to/key.pem

# Docker Registry Secret
kubectl create secret docker-registry docker-secret \
  --docker-username=user \
  --docker-password=pass \
  --docker-server=registry.example.com
```

# Управление Secrets
### Просмотр Secrets
```bash
# Список всех Secrets
kubectl get secrets

# Детальная информация о Secret
kubectl describe secret my-secret

# Получить значения в читаемом виде
kubectl get secret my-secret -o jsonpath='{.data}' | jq '. | map_values(@base64d)'
```
# Обновление Secrets
```bash
# Обновление через kubectl
kubectl create secret generic my-secret \
  --from-literal=username=newadmin \
  --from-literal=password=newpass123 \
  --dry-run=client -o yaml | kubectl apply -f -

# Ротация Secrets
kubectl patch secret my-secret -p '{"metadata":{"labels":{"updated":"'$(date +%s)'"}}}'
```
# Ограничения
-  Размер: Максимум 1 MiB на Secret

-  Кодировка: Данные хранятся в base64 (не шифрование!)

-  Доступ: Только для Pods в том же namespace

-  Обновления: Автоматически обновляются в volumes (кроме subPath)
