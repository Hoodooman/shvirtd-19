# Решение Задание 1

Для упаковки приложения в Helm-чарт и описания необходимых Kubernetes-ресурсов, можно использовать следующую структуру.

| Компонент           | Тип ресурса                    | Количество реплик | Запросы/Лимиты (на контейнер) | Прочие требования                                              |
|---------------------|--------------------------------|-------------------|-------------------------------|----------------------------------------------------------------|
| База данных         | StatefulSet + Headless Service | 3                 | Запросы: 1 CPU, 4Gi памяти    | Отказоустойчивость, постоянное хранилище (PersistentVolume)    |
| Система кеширования | StatefulSet + Headless Service | 3                 | Запросы: 1 CPU, 4Gi памяти    | Отказоустойчивость, собственный кластер (например, Infinispan) |
| Бекенд              | Deployment + Service           | 10                | Запросы: 1 CPU, 600Mi памяти  | Внутренний сервис для общения с фронтендом                     |
| Фронтенд            | Deployment + Service           | 5                 | Запросы: 0.2 CPU, 50Mi памяти | Сервис типа LoadBalancer или ClusterIP + Ingress               |

### Пример структуры Helm-чарта:

```text
my-app-chart/
├── Chart.yaml
├── values.yaml
├── templates/
│   ├── backend-deployment.yaml
│   ├── backend-service.yaml
│   ├── frontend-deployment.yaml
│   ├── frontend-service.yaml
│   ├── db-statefulset.yaml
│   ├── db-service.yaml
│   ├── cache-statefulset.yaml
│   └── cache-service.yaml
└── ...
```

### Конфигурация компонентов

#### База данных и кеш (StatefulSet)

StatefulSet контроллер гарантирует предскатируемость и устойчивость имен подов (например, db-0, db-1, db-2), что критически важно для построения отказоустойчивых кластеров БД и кеша.

Хранилище: Каждому поду в StatefulSet нужен свой независимый том (PersistentVolumeClaim). Это обеспечивает сохранность данных при перезапуске подов.

Сервис: headless-сервис (с clusterIP: None), чтобы обеспечить стабильные DNS-имена для прямого доступа к каждому из подов внутри кластера.

#### Бекенд и Фронтенд (Deployment)

Deployment контроллер идеально подходит для статичных воркеров, позволяет легко управлять обновлениями и масштабированием.

Ресурсы: необходимо задать requests и limits для контейнеров. Это поможет планировщику Kubernetes оптимально размещать поды на нодах и предотвратит исчерпание ресурсов.

Сервис для бекенда: ClusterIP, чтобы фронтенд и другие внутренние компоненты могли к нему обращаться.

Сервис для фронтенда: LoadBalancer для доступа извне или ClusterIP в паре с Ingress-контроллером для продвинутого маршрутизации HTTP-трафика.

#### Дополнительные настройки

Управление конфигурацией: Для хранения конфигураций (например, строк подключения к БД) использовать ресурсы Secret и ConfigMap.

Health-пробы: livenessProbe, readinessProbe и startupProbe для всех компонентов. Это позволит Kubernetes точно определять состояние приложения и корректно перенаправлять трафик.

Отказоустойчивость приложений: убедиться что приложение корректно обрабатывает сигнал SIGTERM, который посылает Kubernetes при начале остановки пода. Это гарантирует graceful shutdown.

Настройки из values.yaml позволяют гибко управлять деплоем. Например, для разработки можно уменьшить количество реплик, а для продакшна — увеличить, не меняя шаблоны.
