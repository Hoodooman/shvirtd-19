### **Postmortem: GitHub Incident 21–22 октября 2018**  
**Дата инцидента:** 21.10.2018, 22:52 UTC – 22.10.2018, 23:03 UTC (24 часа 11 минут)  
**Сервисы:** GitHub Issues, Pull Requests, вебхуки, GitHub Pages  
**Причина:** Каскадный отказ из-за сетевого разделения и сбоя в топологии MySQL :cite[1]:cite[3].  

---

#### **1. Краткое описание**  
21 октября 2018 года GitHub столкнулся с масштабным инцидентом, вызванным **потерей связи между дата-центрами** во время планового обслуживания сетевого оборудования. Это привело к разделению (split-brain) в кластерах MySQL, что потребовало 24 часов на восстановление согласованности данных. Инцидент затронул метаданные (например, Issues, PRs), но не затронул Git-репозитории :cite[1]:cite[3].  

---

#### **2. Хронология инцидента**   
- **22:52 UTC**: Обрыв связи между хабом на восточном побережье США и основным дата-центром из-за замены оптического оборудования. Восстановление заняло 43 секунды, но Orchestrator (система управления MySQL) начал переключение записей на западное побережье :cite[1].  
- **22:54 UTC**: Мониторинг зафиксировал аномалии. К 23:02 команда обнаружила неожиданную топологию репликации :cite[1].  
- **23:13 UTC**: Принято решение вручную восстановить первичные узлы в восточном дата-центре. Из-за расхождений в данных (40 минут записей на западе vs. несколько секунд на востоке) потребовалось восстановление из бэкапов :cite[1].  
- **22 октября, 00:05 UTC**: Начато восстановление данных из удаленных бэкапов (хранились в облаке). Процесс занял часы из-за объема (до 5 ТБ на кластер) :cite[1].  
- **11:12 UTC**: Первичные узлы вернулись в восточный дата-центр, но реплики оставались несинхронизированными :cite[1].  
- **16:24 UTC**: Реплики синхронизированы, сервис восстановлен :cite[1].  

---

#### **3. Корневые причины**  
- **Сетевое разделение**: Кратковременный обрыв связи запустил автоматический failover MySQL через Orchestrator, но данные в двух дата-центрах разошлись :cite[1].  
- **Ограничения восстановления**: Бэкапы MySQL хранились в облаке, их загрузка и подготовка заняли непропорционально много времени :cite[1].  
- **Латентность кросс-датацентровых запросов**: Приложения GitHub не были рассчитаны на задержки при записи в западный дата-центр, что усугубило деградацию сервиса :cite[1].  

---

#### **4. Последствия**  
- **Деградация сервиса**:  
  - Задержки в отображении Issues и PRs.  
  - Приостановка вебхуков и сборки GitHub Pages :cite[1]:cite[3].  
- **Технические компромиссы**: GitHub предпочли **целостность данных** скорости восстановления, что увеличило downtime :cite[1].  

---

#### **5. Уроки и улучшения**   
1. **Тестирование восстановления**: Регулярные проверки полного восстановления кластеров из бэкапов :cite[1].  
2. **Оптимизация Orchestrator**: Настройка конфигурации для предотвращения split-brain :cite[1].  
3. **Локализация данных**: Уменьшение зависимости от кросс-датацентровых операций :cite[1].  
4. **Коммуникация**: Улучшение оповещений пользователей (первый подробный отчет опубликован лишь через 9 часов) :cite[1]:cite[6].
