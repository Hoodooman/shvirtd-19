# Решение Задание 1

- Метрики сервера (инфраструктура)
Загрузка CPU (%)
Потребление RAM (в МБ/ГБ)
Дисковое пространство (свободно/использовано)
Дисковая активность (IOPS, задержка записи/чтения)
- Метрики HTTP-сервиса
Количество HTTP-запросов (по методам и статусам)
Время ответа (latency: p50, p90, p99)
Rate-limiting (если есть ограничения на запросы)
- Метрики бизнес-логики
Количество запущенных вычислений
Время выполнения вычислений
Количество сгенерированных отчетов

CPU и RAM – ключевые метрики для ресурсоемких вычислений.
Диск – отчеты сохраняются на диск, поэтому важно следить за местом и скоростью записи.
HTTP-метрики – помогают оценить доступность и отзывчивость сервиса.
Бизнес-метрики – позволяют связать нагрузку с реальной активностью пользователей.

Этот набор даст понимание здоровья системы и поможет быстро выявлять проблемы (например, нехватку CPU, переполнение диска или рост времени ответа). 
В дальнейшем можно расширять мониторинг в зависимости от потребностей (например, добавить метрики сети, глубины очереди и т. д.).

# Решение Задание 2

Менеджеру продукта важно видеть, насколько хорошо сервис выполняет обязательства перед клиентами.

Метрики качества обслуживания (SLA/SLO/SLI):
- Availability (Доступность) – % времени, когда сервис работал без критических сбоев (например, 99.9%).
- Performance (Производительность) – среднее/95-й перцентиль времени ответа сервиса.
- Error Rate – % ошибочных запросов (5xx ошибки, таймауты).
- Incident Frequency – сколько раз в месяц были сбои, влияющие на клиентов.
- Time to Recovery (MTTR) – как быстро восстанавливаем сервис после сбоя.
  
Клиенто-ориентированные метрики:
- CSAT (Customer Satisfaction) – оценка удовлетворенности клиентов.
- NPS (Net Promoter Score) – насколько клиенты готовы рекомендовать сервис.
- Количество жалоб/тикетов – связанных с производительностью или доступностью.

Визуализация и отчетность:
- Дашборд в Grafana/Google Data Studio с ключевыми SLO.
- Еженедельный отчет с трендами доступности, производительности и инцидентами.
- Объяснение инцидентов – как они повлияли на клиентов и что делается для предотвращения в будущем.

# Решение Задание 3

Вариант один, настроить самостоятельно систему логирования инфраструктуры. Централизованно изолированно хранить для последующего анализа ошибок.

Общая информация о системе:
- /proc/loadavg - средняя загрузка системы
- /proc/meminfo - информация об использовании памяти
- /proc/stat - общая статистика системы (CPU, прерывания и т.д.)
- /proc/uptime - время работы системы

Информация о CPU:
- /proc/cpuinfo - информация о процессоре
- /proc/interrupts - статистика прерываний

Информация о дисках:
- /proc/diskstats - статистика работы дисков
- /proc/partitions - информация о разделах

Сетевая статистика:
- /proc/net/dev - статистика сетевых интерфейсов

# Решение задание 4 

SLA обычно включает все успешные запросы (2xx + 3xx), так как 3xx (редиректы) — это не ошибки, а часть нормального workflow.</br>
Формула расчета SLA = summ_2xx_requests + summ_3xx_requests / summ_all_requests.</br>
Дополнительно необходимо убедиться, что в метриках нет аномально высокого числа 3xx (например, из-за циклических редиректов).

# Решение задание 5

1. Pull-системы (например, Prometheus, Nagios)

🔹 Плюсы:</br>
✅ Централизованное управление – сервер сам запрашивает данные с агентов, что упрощает контроль.</br>
✅ Безопасность – агентам не нужно открывать входящие соединения, только исходящие к серверу.</br>
✅ Гибкость – можно динамически добавлять/удалять цели мониторинга без изменения конфигурации агентов.</br>
✅ Надёжность – сервер повторяет запросы при проблемах с сетью.</br>
✅ Эффективность – можно настраивать частоту опроса для разных метрик.

🔹 Минусы:</br>
❌ Задержки данных – метрики обновляются только при опросе (не подходит для real-time).</br>
❌ Масштабируемость – при большом количестве целей сервер может не справляться с нагрузкой.</br>
❌ Сложность в облаках – динамические IP-адреса и автоскейлинг требуют service discovery.</br>

2. Push-системы (например, Graphite, InfluxDB, Zabbix (может работать в push-режиме))
   
🔹 Плюсы:</br>
✅ Реальное время – агенты отправляют данные сразу, задержки минимальны.</br>
✅ Масштабируемость – сервер принимает данные, а не опрашивает тысячи узлов.</br>
✅ Гибкость данных – можно отправлять метрики по событию (например, при превышении порога).</br>
✅ Проще в облаках – агенты сами регистрируются в системе, не нужен discovery.</br>

🔹 Минусы:</br>
❌ Риск потери данных – если сервер недоступен, метрики могут пропасть (нужен буфер на стороне агента).</br>
❌ Безопасность – сервер должен принимать входящие соединения от агентов (риск DDoS).</br>
❌ Сложность управления – при изменении сервера нужно перенастраивать всех агентов.</br>

Вывод:</br>
Pull лучше для статичных сетей, где важны безопасность и контроль.</br>
Push предпочтительнее в динамических средах (облака, микросервисы), где важна оперативность.</br>
Часто используют гибридные системы (например, VictoriaMetrics поддерживает оба подхода).

# Решение Задание 6

1. Pull-модель (забирают данные сами)</br>
Prometheus – работает по Pull-модели: сервер сам опрашивает цели (targets) по HTTP.</br>

2. Push-модель (агенты отправляют данные)</br>
TICK (Telegraf + InfluxDB + Chronograf + Kapacitor) – Telegraf (агент) отправляет данные в InfluxDB (Push).</br>
Nagios – традиционно использует Push через NRPE (Nagios Remote Plugin Executor) или NSCA (Nagios Service Check Acceptor).</br>

3. Гибридные (поддерживают обе модели)</br>
Zabbix – может работать в обеих моделях:</br>
Pull – Zabbix-сервер сам опрашивает агентов.</br>
Push – агенты могут отправлять данные через Zabbix Trapper или Active Checks.</br>
VictoriaMetrics – хоть и совместима с Prometheus (Pull), но также поддерживает Push через /api/v1/import/prometheus и другие API.
