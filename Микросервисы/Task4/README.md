# Решение Задание 1

Решение задания идеально ложиться на парадигму современной контейнерной оркестрации. Использование платформы Kubernetes в связке с дополнительными инструментами будет оптимальным для создания полнофункциональной, отказоустойчивой и безопасной системы.

### Архитектурное решение 
- Kubernetes:<br>Ядро системы. Оркестрация контейнеров, управление жизненным циклом приложений, секретами, конфигурациями.
- Ingress Controller (например, Nginx Ingress):<br>Обеспечивает доступ к сервисам извне, маршрутизацию и балансировку L7-трафика.
- Horizontal Pod Autoscaler (HPA):<br>Обеспечивает автоматическое горизонтальное масштабирование подов на основе метрик CPU/RAM или кастомных метрик.
- Prometheus + Grafana:<br>Система мониторинга для сбора метрик работы кластера и приложений.
- ExternalDNS:<br>Автоматическое управление DNS-записями для сервисов.
- Cert-manager:<br>Автоматическое получение и продление SSL/TLS-сертификатов от Let's Encrypt.

### Соответсвие требованиям
- Поддержка контейнеров:<br>Kubernetes является самой популярной платформой для оркестрации Docker-контейнеров и других контейнерных форматов (например, containerd).
- Обнаружение сервисов и маршрутизация запросов:<br>
  Обнаружение сервисов: В Kubernetes встроен механизм Service. Каждый сервис получает стабильный IP-адрес и      DNS-имя внутри кластера (например, my-service.namespace.svc.cluster.local). Другие приложения могут            обращаться к нему по этому имени, не заботясь о том, на каких именно узлах работают поды.<br>
  Маршрутизация запросов извне: Эту задачу решает Ingress Controller (например, на основе Nginx).
- Обеспечение возможности горизонтального масштабирования:<br>Kubernetes позволяет вручную масштабировать количество копий приложения (подов) одной командой kubectl scale deployment/my-app --replicas=5.
- Обеспечение возможности автоматического масштабирования:<br>Для этого используется встроенный механизм Horizontal Pod Autoscaler (HPA). HPA автоматически увеличивает или уменьшает количество подов в Deployment'е на основе наблюдаемой загрузки CPU/RAM или кастомных метрик (например, количества сообщений в очереди RabbitMQ).
- Явное разделение ресурсов (сеть)<br>Внутренние сервисы: Используются ресурсы типа Service с типом ClusterIP. Этот   тип назначает сервису внутренний IP-адрес, доступный только внутри кластера Kubernetes. Внешний трафик до них не             доходит.<br>Используются ресурсы типа Service с типом NodePort или LoadBalancer, и прежде всего — Ingress. Ingress Controller является единственным компонентом, который "выставлен" наружу. Все правила доступа к внутренним сервисам из        интернета явно описываются в ресурсах Ingress. Таким образом, мы имеем четкое разделение: всё, что не описано в Ingress, по умолчанию недоступно извне.
- Конфигурирование и безопасное хранение чувствительных данных:<br>ConfigMap: Предназначен для хранения        некритичной конфигурации в виде пар "ключ-значение" (например, настройки флагов, конфигурационные файлы).    Данные хранятся в незашифрованном виде (base64).<br>Secret: Предназначен для хранения чувствительных         данных, таких как пароли, OAuth-токены, SSH-ключи. Данные хранятся в зашифрованном виде (base64, но с        возможностью включения шифрования на отдыхе - Encryption at rest). Секреты могут быть смонтированы в поды    как файлы или переданы как переменные среды

### Обоснование выбора
- Kubernetes выбран как отраслевой стандарт: Он обладает наибольшим сообществом, экосистемой инструментов и документацией. Его возможности покрывают все заявленные требования "из коробки" или с помощью стандартных аддонов.
- Горизонтальное и автоматическое масштабирование являются базовыми функциями K8s (HPA), что делает систему эластичной и экономически эффективной.
- Безопасность: Механизмы Secrets, Network Policies и модель доступа RBAC позволяют построить безопасную среду, соответствующую modern DevOps-практикам.
- Экосистема и переносимость: Приложение, развёрнутое в K8s, становится переносимым. Его можно запустить на любом другом K8s-кластере у любого облачного провайдера или в собственном дата-центре (гибридная облачная модель), что обеспечивает гибкость и избегает lock-in
